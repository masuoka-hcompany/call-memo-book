# Cloudflare アカウント運用方針

勉強会および社内アプリ開発で利用する Cloudflare アカウントの運用方針をまとめる。設定手順は [cloudflare-setup.md](./cloudflare-setup.md) を参照。

## 1. 基本方針

- **勉強会中は、参加者が各自の Cloudflare アカウント（無料プラン）で開発する。**
  - 他の参加者のリソースと干渉しないため、気楽に試せる。
  - ログインには個人の Google アカウント、またはワンタイム PIN（メール認証）を使う。
- **本採用となったアプリは、会社の Cloudflare アカウントへ移して運用する。**
  - 会社アカウントでは Google Workspace でログインし、社内ユーザーだけに公開する。
  - アプリのコードはそのまま使い、環境ごとの値（Access のチームドメイン・AUD タグなど）を差し替えるだけで移行できるようにしておく。

### 各自のアカウントで開発する理由

| 観点     | 内容                                                                         |
| -------- | ---------------------------------------------------------------------------- |
| 干渉     | 他人の Worker / D1 を誤って操作・削除する心配がない                          |
| 上限     | 無料プランの上限（リクエスト数・CPU 時間など）を他の参加者と共有しない       |
| 準備     | 会社アカウントへの招待やロール設計が不要で、各自がすぐに始められる           |
| 移行     | 移行作業は発生するが、採用されるのは1つだけで、環境依存値の差し替えで済む     |

## 2. プラン

- 各自のアカウントは **無料プラン（Workers Free）** で十分。上限を超えても課金は発生せず、リクエストがエラーになる。
- Zero Trust（Cloudflare Access）も無料プランで使える（執筆時点で50ユーザーまで）。
- CPU 時間の上限が厳しいため、重い処理を書くとエラーになる場合がある。
- 最新の上限値は公式の料金ページで確認すること。
  - https://developers.cloudflare.com/workers/platform/pricing/
  - https://developers.cloudflare.com/d1/platform/limits/

## 3. 勉強会中のアカウント（各自）

### 作成するもの

| もの                    | 内容                                                                      |
| ----------------------- | ------------------------------------------------------------------------- |
| Cloudflare アカウント   | 無料プラン。会社のメールアドレスで作成してよい                            |
| Zero Trust の組織       | チームドメイン `<チーム名>.cloudflareaccess.com` を各自決める             |
| ログイン方法            | ワンタイム PIN（推奨・設定不要）、または Google（Google Cloud で OAuth クライアントを作成） |
| Worker / D1             | `npm run setup` で作成する。名前は各自で自由に決めてよい                  |
| Access アプリケーション | 自分の Worker の workers.dev を保護し、自分のメールアドレスだけを許可する |

### Access のポリシー

- 許可するユーザーは**メールアドレスを明示的に列挙する**（例: 自分の Gmail アドレス）。
- **「`@gmail.com` で終わる」のようなドメイン指定にしないこと。** 世界中の Gmail ユーザーに公開することになる。
- アプリ側でも Access の JWT を検証する（Access の設定漏れに対する防御）。

## 4. API トークン

- 自分のアカウントで API トークンを発行する。権限は Workers / D1 の編集に必要な範囲に絞る（テンプレート「Edit Cloudflare Workers」に D1 の Edit を追加する）。
- ローカル開発（Docker 内の Wrangler）では、環境変数 `CLOUDFLARE_API_TOKEN` で渡す。
  - コンテナ内では `wrangler login`（ブラウザ認証）が正常に動作しないため。
- トークンはリポジトリにコミットしない。

## 5. データの取り扱い

- 勉強会・検証中のアプリには**ダミーデータのみ**を投入する。
- 実データの投入は、会社アカウントへ移行した後に限る。

## 6. 本採用アプリの本番化（会社アカウント）

管理者が会社アカウントを用意し、採用されたアプリを移す。

1. 会社アカウントの Zero Trust に、ログイン方法として **Google Workspace** を追加する。
   - 会社の Google Cloud プロジェクトで「内部」の OAuth クライアントを作成する（Google Workspace の管理者権限が必要）。
2. Access のポリシーを「メールドメインが `h-company.co.jp`」または Google グループ指定にする。
3. 本番用の Worker / D1 を作成する。D1 のスキーマはマイグレーションファイルから適用する（ダッシュボードでの直接変更は禁止）。
4. 必要に応じて独自ドメインを割り当て、Access の対象にする。
5. アプリの環境依存値（`ACCESS_TEAM_DOMAIN` / `ACCESS_AUD` など）を会社アカウントの値に差し替える。シークレットは `wrangler secret put` で設定する。
6. 本番へのデプロイは CI からのみ行う（GitHub Secrets に会社アカウントの API トークンとアカウント ID を設定する）。
7. 勉強会のデータは移行しない。各自のアカウントの Worker / D1 は `npm run destroy` で削除してよい。

### 会社アカウントの権限

| 対象           | ロール                                                         |
| -------------- | -------------------------------------------------------------- |
| 管理者（数名） | Super Administrator                                            |
| 開発メンバー   | 本番アプリの Worker に対する必要最小限のロール（Worker 単位で付与できる） |
| CI             | 本番アプリの Worker に対する Editor 相当のアカウント API トークン |

## 7. 事前準備チェックリスト

### 参加者（勉強会の前日まで）

- [ ] Cloudflare アカウントを作成し、ダッシュボードにログインできる
- [ ] Zero Trust のチームドメインを決めた（ワンタイム PIN でログインできる状態）
- [ ] 自分の API トークンを発行し、アカウント ID と一緒に `.env` に設定した

### 管理者（本採用が決まったら）

- [ ] 会社アカウントと Zero Trust の用意（Google Workspace 連携・社内ドメイン限定ポリシー）
- [ ] 本番用の Worker / D1 の作成と、CI 用の API トークンの発行
- [ ] 開発メンバーの招待とロール付与
