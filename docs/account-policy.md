# Cloudflare アカウント運用方針

勉強会および社内アプリ開発で利用する Cloudflare アカウントの運用方針をまとめる。

## 1. 基本方針

- **会社所有の Cloudflare アカウントを1つ用意し、参加者をメンバーとして招待する。**
- 個人アカウントは使用しない。
- 参加者は各自、自分の名前を付けた Worker / D1 を作成して開発する。
- 本採用となったアプリは、同アカウント上で本番用の名前・ドメインに付け替えて運用する。

### 会社アカウントに集約する理由

| 観点 | 内容 |
|---|---|
| 認証（Access） | Google Workspace 連携を管理者が一度設定すれば、全員が社内アカウントでログインできる |
| 本番移行 | アカウント間のデータ・設定移行が不要。採用アプリをそのまま本番化できる |
| 管理 | 作成物を一覧で把握でき、放置アプリの削除や退職者対応を会社側で行える |

## 2. プラン

- **無料プラン（Workers Free）で運用する。** 現在の参加人数であれば上限内に収まる見込み。
- 無料プランの上限（リクエスト数・CPU 時間・D1 データベース数など）は**アカウント単位で全員共有**となる点に注意する。
  - 上限を超えても課金は発生せず、リクエストがエラーになる。
  - 不要になった Worker / D1 は速やかに削除し、枠を空ける。
  - CPU 時間の上限が厳しいため、重い処理を書くとエラーになる場合がある。
- 参加人数の増加や本番アプリの負荷増加により上限に近づいた場合は、Workers Paid プランへの切り替えを検討する。
- 最新の上限値は公式の料金ページで確認すること。
  - https://developers.cloudflare.com/workers/platform/pricing/
  - https://developers.cloudflare.com/d1/platform/limits/

## 3. メンバーと権限

### 招待

- 管理者が参加者を会社メールアドレスでアカウントに招待する。
- 参加者は勉強会前日までに招待を承認し、ログインできることを確認する。

### 付与するロール

| 対象 | ロール |
|---|---|
| 管理者（数名） | Super Administrator |
| 参加者 | Workers / D1 の操作に必要なロールのみ（Super Administrator は付与しない） |

> **注意:** Cloudflare のロールはアカウント単位で、「自分の Worker だけ操作できる」という制限はできない。
> 参加者は他人の Worker / D1 も操作できてしまうため、後述の命名規則を徹底する。

## 4. 命名規則

他人のリソースとの衝突・誤操作を防ぐため、すべてのリソース名に作成者名を付ける。

| リソース | 命名規則 | 例 |
|---|---|---|
| Worker | `<氏名>-<アプリ名>` | `masuoka-todo` |
| D1 データベース | `<氏名>-<アプリ名>-db` | `masuoka-todo-db` |

- 氏名はローマ字・小文字・ハイフン区切りとする。
- 本採用時は本番用の名前（作成者名なし）で作り直す。

## 5. API トークン

- 各参加者が**自分のユーザーで** API トークンを発行する（共有トークンは使わない）。
- トークンの対象は会社アカウントのみに限定し、権限は Workers / D1 の編集に必要な範囲に絞る。
- ローカル開発（Docker 内の Wrangler）では、環境変数 `CLOUDFLARE_API_TOKEN` で渡す。
  - コンテナ内では `wrangler login`（ブラウザ認証）が正常に動作しないため。
- トークンはリポジトリにコミットしない。

## 6. アクセス制御（Cloudflare Access）

- 管理者が Zero Trust の初期設定を行う。
  - IdP として Google Workspace を連携する。
  - 社内ドメイン（`@h-company.co.jp`）のユーザーのみ許可するポリシーを作成する。
- 勉強会中のアプリは `*.workers.dev` で公開されるため、**workers.dev およびプレビュー URL に Access を適用する**。
  - ワイルドカード指定により、各自が作成した Worker にも自動で適用されるようにする。
- アプリ側でも Access の JWT を検証する（Access 設定漏れ時の防御）。
- Zero Trust 無料枠のユーザー数上限（執筆時点で50ユーザー）に収まるか確認する。

## 7. 本採用アプリの本番化

1. 本番用の名前で Worker / D1 を作成する。
2. D1 のスキーマはマイグレーションファイルから適用する（ダッシュボードでの直接変更は禁止）。
3. 必要に応じて独自ドメインを割り当て、Access の対象に追加する。
4. シークレットを `wrangler secret put` で設定する。
5. 本番へのデプロイは CI からのみ行う。
6. 勉強会で作成した各自の Worker / D1 は削除する。

### 将来の検討事項

- 参加者のロールでは本番アプリも操作できてしまう。権限分離が必要になった場合は、**検証用アカウントと本番用アカウントを分け**、本番用アカウントへのデプロイ権限は CI のみに持たせる。

## 8. データの取り扱い

- 勉強会・検証中のアプリには**ダミーデータのみ**を投入する。
- 実データの投入は本番化後に限る。

## 9. 事前準備チェックリスト

### 管理者

- [ ] 会社アカウントを作成（無料プラン）
- [ ] 参加人数分の Worker / D1 が無料プランの上限内に収まることを確認
- [ ] Zero Trust の初期設定（Google Workspace 連携・社内ドメイン限定ポリシー）
- [ ] workers.dev / プレビュー URL への Access 適用
- [ ] 参加者の招待とロール付与
- [ ] Zero Trust のユーザー数上限の確認

### 参加者

- [ ] 招待メールを承認し、ダッシュボードにログインできる
- [ ] 自分の API トークンを発行した
- [ ] 命名規則を確認した
