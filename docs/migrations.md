# マイグレーションの決まり

D1 のスキーマは `migrations/` の SQL で管理する。リモートへの適用は `wrangler d1 migrations apply`（`npm run deploy` の中で実行される）。
DB の設計は `docs/db/`、ハーネス全体の方針は `docs/harness.md`。

機械で確かめられる決まりは、`npm run migrations:check`（`scripts/check-migrations.ts`）が確かめる。CI と `npm run check` で実行される。

## 1. 追加のしかた

1. `npx wrangler d1 migrations create DB <名前>` で、`migrations/` に次の番号のファイルを作る（`0003_<名前>.sql` の形。名前は英小文字・数字・`_`）
2. SQL を書く。`docs/db/` の設計書も一緒に直す
3. `npm run db:migrate:local` でローカルの D1 に当て、`npm run check` を通す（テストは、テスト用の D1 にすべてのマイグレーションを当ててから動く）

ダッシュボードや `wrangler d1 execute --remote` で、スキーマを直接変えない。

## 2. リモートに当てたものは書き換えない

- リモートに当てたマイグレーションは、書き換えない・消さない・名前を変えない。直すときは、新しいマイグレーションを足す（wrangler は適用済みのファイルを当て直さないので、書き換えてもリモートには反映されず、ローカルやテストとだけ食い違う）
- 戻すためのマイグレーション（down）は作らない。戻すときも、新しいマイグレーションを足す
- **まだ当てていないマイグレーションは、書き換えてよい**

### migrations/APPLIED

どこまでリモートに当てたかを、`migrations/APPLIED` に 4 桁の番号で書く（1 つも当てていなければ `0000`）。検査は、この番号までのファイルを「書き換えてはいけない」とみなす。

- **更新するのは人間だけ。** リモートに当てたあと（`npm run deploy` のあと）、`npx wrangler d1 migrations list DB --remote` で未適用のものがないことを確かめてから、番号を進めてコミットする
- AI エージェントは `APPLIED` を書き換えない（Claude Code では `.claude/settings.json` で拒否している）
- `APPLIED` は Cloudflare の適用の記録そのものではなく、人間が写した記録。食い違いに気づいたら、リモートの記録を正として直す

## 3. 検査の中身

`npm run migrations:check` は、次の点を確かめる。

| 検査 | 失敗する例 |
|---|---|
| ファイル名が「4 桁の番号_名前.sql」 | `3_add.sql`、`0003_Add.sql` |
| 番号が重なっていない | 2 つのブランチが、それぞれ `0003_...` を作ってマージした |
| `APPLIED` があり、その番号のマイグレーションがある | `APPLIED` を消した |
| `APPLIED` の番号までのファイルが、マージ先のブランチと同じ | 当てたマイグレーションを書き換えた・消した・名前を変えた |
| 新しいファイルの番号が、`APPLIED` より大きい | 当てた番号より前に、ファイルを差し込んだ |
| `APPLIED` が、マージ先のブランチより前に戻っていない | `0002` を `0001` に戻した |
| まだ当てていないファイルに、書かないと決めた文がない | `PRAGMA foreign_keys`（D1 では効かない）、`BEGIN TRANSACTION`・`COMMIT`・`ROLLBACK`（D1 がマイグレーションごとにまとめて反映する）、`SAVEPOINT`（D1 でエラーになる） |

- 比べる相手は、PR ではマージ先のブランチ、手元では `origin/main`（環境変数 `MIGRATIONS_BASE` で変えられる）
- 番号が重なったときは、あとからマージするほうが番号を付け直す
- 検査は、決まりを破る変更を通しにくくするためのもの。SQL が正しいことまでは確かめない。それはテストと、ローカルの D1 への適用で確かめる

## 4. デプロイの順番と、壊さない変更

`npm run deploy` は「マイグレーションを当てる → Worker を入れ替える」の順に動く。その間は、**古いコードが新しいスキーマで動く**。そのため、古いコードが壊れない形で変える。

- **列・テーブルを足す**：足す列は、NULL を許すか、DEFAULT を付ける（古いコードの INSERT が失敗しないように）
- **列・テーブルを消す**：2 回に分ける
  1. 1 回目：コードからその列の読み書きをなくして、デプロイする
  2. 2 回目：列を消すマイグレーションを足して、デプロイする
- **列の名前を変える**：足す → コードを切り替える → 消す、の順に分ける

## 5. テーブルの作り直し（まだ手順を決めていない）

SQLite は、CHECK 制約・列の型・NOT NULL を `ALTER TABLE` で変えられない。インデックスや制約に関わる列は、`DROP COLUMN` もできない。変えるには、新しいテーブルを作って行を移し、古いテーブルを消して名前を変える「作り直し」が要る。

このスキーマは CHECK 制約を多く使っているので、入力のルールが変わると作り直しになる。**作り直しが必要になったら、手順を人間と決めてから書く。** 分かっている注意点：

- D1 では `PRAGMA foreign_keys = OFF` が効かない。外部キーの確認を遅らせるには `PRAGMA defer_foreign_keys = on` を使う
- ほかのテーブルから参照されているテーブル（`companies`・`contacts`・`recipients`・`users`）の作り直しは、とくに注意が要る
- インデックス（とトリガー）は `DROP TABLE` で消えるので、作り直す
- 行を移すときは、列を `SELECT *` ではなく 1 つずつ書く。論理削除済みの行も移す
- 本番に当てる前に、データを入れたローカルの D1 でリハーサルをし、作り直す前とあとで、件数と中身を比べる

## 6. データ

| 種類 | 置き場所 |
|---|---|
| 本番にも要る初期データ | マイグレーションに INSERT で書く |
| ローカルの開発用のデータ | `seed/seed.sql`（`npm run db:seed:local`）。実データを入れない |
| テスト用のデータ | テストごとに、必要な分だけ作る。全テストで共有する大きなデータは作らない |

## 7. 戻し方

- スキーマの変更を取り消すときは、取り消すためのマイグレーションを足す
- データまで戻す必要があるときの手順（D1 の Time Travel）は、まだ決めていない（`docs/harness.md` 5章）。利用が始まる前に決める
